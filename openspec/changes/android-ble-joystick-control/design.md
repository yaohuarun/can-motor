# Design

## Context

现有 Python 程序把参数解析、固定目标换算、CAN 生命周期、启动观察、反馈处理和退出停机集中在一次命令行运行中。新功能需要 Android 与 Ubuntu 两端长期协作，并允许目标在运行中更新；安全停车不能依赖 Android 进程或 BLE 链路及时报告断开。

Ubuntu 使用 BlueZ。BlueZ 通过 system D-Bus 的 `org.bluez.GattManager1` 注册本地 GATT 服务，通过 `org.bluez.LEAdvertisingManager1` 注册 peripheral 广播；Android 原生 BLE API 作为 Central/GATT Client 连接。部署前必须确认工控机适配器支持 LE Peripheral、Advertising 和 GATT Server。

## Goals / Non-Goals

**Goals:**

- 让 Android 手柄输入以固定频率、低延迟地更新工控机目标。
- 让工控机独立拥有授权、校验、回中解锁、看门狗和最终停车权。
- 复用并测试现有差速换算、限速、CAN 反馈和退出停机逻辑。
- 保持协议可版本化，并为跨端测试提供固定二进制测试向量。

**Non-Goals:**

- 不把 BLE 链路或 Android App 视为功能安全认证组件，也不替代硬件急停。
- 不支持 iOS、Windows 工控机、互联网转发、多车组网或多个客户端共同控制。
- 不在第一版通过 BLE 修改电机最高转速、方向、保护阈值等持久配置。
- 不改变现有命令行固定目标的默认行为。

## Decisions

### 1. Ubuntu 是 BLE Peripheral/GATT Server

工控机广播自定义 128-bit 服务 UUID，Android 扫描后作为 GATT Client 主动连接。服务包含：只写运动命令特征、可通知状态特征、只读能力特征。

选择该方向是因为工控机服务可常驻并集中掌握 CAN 与安全状态，Android 官方 API 对 Central/GATT Client 支持成熟。替代方案是 Android 做 GATT Server，但会让工控机承担扫描和手机发现，并使 Android 生命周期更容易影响可用性；经典蓝牙 RFCOMM 已被用户排除。

### 2. 直接使用 BlueZ D-Bus，并由 systemd 托管网关

Python 网关通过异步 D-Bus 客户端实现 BlueZ ObjectManager、GattManager 和 LEAdvertisingManager 所需对象，systemd 负责启动、重启和最小权限。D-Bus policy 只授权专用系统用户注册服务与广告，CAN 设备权限通过组或 udev 配置提供。

选择直接对接 BlueZ API可显式控制权限、连接和生命周期，避免依赖行为不透明的串口模拟层。实现前先提供只读环境诊断，确认 `hci0` 的 GATT Manager、Advertising Manager 和外设能力；不满足时拒绝启动 CAN 控制。

### 3. 使用固定 20 字节、小端、版本化命令

命令特征采用 Write Without Response，以 20 Hz 发送最新状态，不建立历史队列。V1 命令恰好 20 字节，可在默认 ATT MTU 下发送：

| 偏移 | 类型 | 内容 |
|---:|---|---|
| 0 | `uint8` | 协议版本，V1=`1` |
| 1 | `uint8` | 标志，bit0=`joystick_centered`，其余必须为 0 |
| 2 | `uint16` | 保留，必须为 0 |
| 4 | `uint32` | 当前连接会话标识 |
| 8 | `uint32` | 单调递增序号 |
| 12 | `float32` | 线速度，m/s |
| 16 | `float32` | 角速度，rad/s |

ATT 已提供链路层完整性；应用层通过固定长度、版本、保留位、会话、序号、有限值和范围完成语义校验，不再增加 CRC。序号使用无符号模运算比较并拒绝重复；每次 BLE 连接由网关生成随机非零会话标识，App 从能力/状态特征读取后原样回传。

选择二进制定长格式是为了限定解析面、适配默认 MTU，并避免 JSON 在 20 Hz 下产生长度、编码和分配开销。协议编解码在 Kotlin 与 Python 两端使用同一组黄金测试向量。

### 4. 状态通知和能力读取分离

能力特征提供协议版本、最大线速度、最大角速度、50 ms 推荐周期和 300 ms 超时；连接期间不变。状态特征使用不超过 20 字节的 V1 固定帧，包含会话、最近接受序号、控制状态、停车原因、量化后的当前目标以及左右故障摘要。电机详细遥测仍保留在工控机控制台，避免第一版状态帧膨胀。

状态通知是可观察性和确认机制，不参与 CAN 实时调度。通知拥塞或失败只记录诊断，不能延迟看门狗或 CAN 周期。

### 5. 工控机拥有独立安全状态机

状态机为 `IDLE → WAIT_CENTER → ARMED → SAFE_STOP`。连接进入 `WAIT_CENTER`；只有当前会话的零速度且 `joystick_centered=1` 的有效命令才能进入 `ARMED`。超时、断链、非法命令、超速、CAN 故障或服务异常进入 `SAFE_STOP`，立即原子地清除旧目标并把下一 CAN 周期目标设为零；恢复运动必须创建/重置会话并再次回中。

300 ms 看门狗使用 `time.monotonic()`，仅由完整有效且属于当前会话的新序号命令刷新。Android 仍会在松手时立即连续发送零速，但这只是更快的正常路径，不能替代网关看门狗。

### 6. 提取可复用的电机控制会话

把现有一次性主循环拆成不依赖 BLE 的控制核心：配置并打开 CAN、完成启动观察、校验并更新车体目标、按周期发送最新目标、处理反馈、进入安全零速、关闭时发送零速与失能。命令行入口继续用固定目标驱动该核心；BLE 网关在同一事件循环或明确同步边界上更新最新目标。

目标更新采用单槽覆盖模型：BLE 回调只提交最新已验证目标及时间戳，CAN 周期读取快照；不会为每条 BLE 写入排队。这样可避免旧指令积压，也便于用虚拟时钟测试 300 ms 边界。

### 7. Android 采用原生 Kotlin 单向状态流

Android 工程使用 Kotlin、Jetpack Compose 和 ViewModel/StateFlow。BLE 层串行化所有 GATT 操作；控制循环每 50 ms 读取最新手柄状态并写入一帧，不从触摸回调直接并发写 GATT。最低支持 Android 8（API 26），并分别处理 Android 12+ 的 `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` 与旧版本扫描权限。

手柄使用圆形边界与中心死区，松手自动回中。App 只在前台控制页面、当前会话已确认解锁且用户正在触摸时产生非零目标；生命周期离开时先排队零速并终止发送循环。

### 8. 配对授权和单控制端

命令特征要求加密且经过身份验证的写入；部署时由管理员完成配对并在 Ubuntu 标记可信设备。网关配置允许的设备身份，连接身份不在允许列表时不授予会话。第一版只允许一个活动控制客户端，避免仲裁语义不明确。

配对和允许列表只能降低误连接风险，不能替代物理隔离和硬件急停。密钥或手机丢失时，管理员必须能从 Ubuntu 撤销设备并重新配对。

## Risks / Trade-offs

- [300 ms 在 2.53 m/s 时理论上仍可能前行约 0.76 m，且不含制动距离] → 首次测试架空驱动轮并逐级提速；保留硬件急停，实车测量后再决定是否缩短超时。
- [Ubuntu 蓝牙适配器或驱动不支持可靠外设广播] → 在打开 CAN 前执行能力诊断；文档列出合格适配器要求和 BlueZ 检查命令。
- [Android 厂商 BLE 栈存在写入节流或回调差异] → 单一 20 Hz 写循环、Write Without Response、状态序号确认，并至少用两类真实设备做断链与后台测试。
- [重构现有主循环可能引入停车回归] → 先以虚拟时钟和假 CAN 后端锁定原命令行行为，再接入 BLE。
- [状态通知丢失导致 App 显示滞后] → App 根据会话和序号丢弃旧状态；控制安全完全由工控机状态机决定。
- [systemd 自动重启可能重新广播] → 每次进程启动和连接都生成新会话，默认零速且必须重新回中，绝不恢复旧目标。

## Migration Plan

1. 先提取并回归验证可复用电机控制核心，保持现有 CLI 测试全部通过。
2. 实现和测试共享 BLE 帧协议及 Ubuntu 安全状态机，使用假时钟和假 CAN 验证全部停车路径。
3. 在 Ubuntu 安装 BlueZ/D-Bus 依赖，验证只广播和授权连接，不连接真实 CAN。
4. 构建 Android App，以假 GATT 层测试手柄、生命周期和重连，再与 Ubuntu 网关联调零速命令。
5. 架空驱动轮后连接 CAN，依次验证回中解锁、松手、300 ms 超时、断链、App 崩溃和网关退出。
6. 验证通过后再安装 systemd 服务并逐级提高速度；回滚时停用服务、撤销 D-Bus policy，并继续使用原命令行入口。
